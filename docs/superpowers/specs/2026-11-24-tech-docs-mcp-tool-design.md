# 技術ドキュメントDBを MCP から検索する（context7 の置き換え）設計

日付: 2026-11-24（2026-11-26 に vLLM 版・GB10 配置へ読み替え）

> **出どころ。** 初版は Ollama 版（Hide369/local-llm-rag、`docs/superpowers/specs/` の同名ファイル、
> PR #122）で書いた。移行先では Ollama 版を廃止して本リポジトリ（vLLM 版）へ移るため、
> 配置を GB10（systemd + Nginx）に、クライアントを Claude Code だけに読み替えた。
> 方式（4.1〜4.5）は変えていない。変えたのは 3・4.6〜4.8・6 である。

## 1. 目的

VS Code の Claude Code（GB10 の gpt-oss-120b）が OSS ライブラリの API や設定を調べる
とき、context7 ではなく、GB10 に置いた技術ドキュメントDB（`docs_store.sqlite3`）を
引くようにする。

利用者の動機は次の2つである（2026-11-24 の会話）。

1. **検索語を社外に出したくない。** context7 は「こちらから内容を送る唯一の経路」で
   あり、クエリ文の書き方を細かく制限する必要があった。経路そのものを無くす。
2. **オフラインで使いたい。** GB10 とクライアントが外へ出られなくても、ライブラリの
   調べものができる。

対象のクライアントは Claude Code だけである。Codex 向けの構成・文書と `AGENTS.md` は
考慮しない（2026-11-26 利用者の指示）。

## 2. ゴール・非ゴール・失敗の条件

**ゴール**

- 既存の MCP サーバ（`scripts/rag_mcp_server.py`、GB10 の `rag-mcp.service`、外からは
  Nginx の `/mcp`）に技術ドキュメント検索のツールを1つ足し、Claude Code から呼べる
- 検索時に GB10 から外部への通信が1本も出ない（リランカーの HEAD を含む）
- クライアントから context7 を外し、`CLAUDE.md` の指示を技術DBに切り替える手順がある

**非ゴール**

- context7 のデータそのものの取り込み（一括取得の口が無く、利用規約も未確認。
  context7 も公式ドキュメントから作っているので、元の資料を `fetch_docs` で取る）
- 収録ライブラリを増やすこと（`docs_sources.toml` のまま。増やし方は既存の
  [コーディング対応ライブラリ.md](../../コーディング対応ライブラリ.md) 5節に従う）
- 検索サーバ上での日本語→英語の翻訳（後述 4.3）
- 資料の自動更新（`fetch_docs` は外へ出るので、人が外に出られる機械で実行する）
- Web 画面（`rag_web/`）の変更。技術ドキュメントを画面の管理者専用にする件は
  別の設計書（`2026-11-26-docs-corpus-admin-only-design.md`）が扱う。利用者の
  コーディングは VS Code で行うので、技術DBを利用者に届ける経路はこの MCP ツールになる

**失敗の条件（動いても失敗とみなすもの）**

- 社内資料の検索の挙動・文言が変わる
- 技術DBの結果に社内資料向けの注意書き（「社内固有の事項は推測しない」）が付く、
  またはその逆
- 0件のときにモデルが context7 やウェブ検索で補いにいく
- 検索のたびに huggingface.co へ HEAD が出る（オフラインで初回検索が遅れる・失敗する）

## 3. 制約

- 技術DBの本文は英語である。日本語の検索語では当たらず、採否はリランカーの床
  （`DOCS_RERANK_FLOOR = 1.0`、`ingest/retrieval.py`）で決まる。床は「この文章が
  問いに答えているか」を測った値なので、依頼文ではなく疑問文で渡す必要がある
  （`ingest/query_translation.py` の `topic_query` の docstring の実測）
- 外から MCP に届くのは Nginx の `location = /mcp`（Bearer トークン）の1経路だけで
  ある。MCP サーバ自身は `127.0.0.1:8080` にだけ bind する（`deploy/gb10/`）
- DBのパスは `store.DOCS_DB_PATH` を使い、引数や環境変数で受け取らない
  （食い違うと空のDBが黙って作られる。`_open` の docstring と同じ理由）
- 2つのDBとも、記録された埋め込みモデルが `VLLM_EMBED_MODEL` と一致していなければ
  開いた時点で止まる（`store.EmbeddingMismatchError`）。MCP サーバの埋め込み設定は
  1つなので、技術DBも社内資料と同じモデルで作られている必要がある
- 検索は `_search_lock` で直列化したままにする（複数PCからの同時アクセスの前提）

## 4. 方式

### 4.1 検討した案

| 案 | 中身 | 採否 |
| --- | --- | --- |
| **A. 既存サーバにツールを1つ足す** | `search_tech_docs` を追加し、同じプロセス・同じ `/mcp` で公開 | **採用**（利用者が選択） |
| B. 技術DB用に別プロセスを立てる | 同じスクリプトを別ポートで起動 | Nginx の経路・トークン・systemd のユニットがもう1組要り、リランカーが2つ載る |
| C. 1つのツールに `corpus` 引数を足す | 引数で社内資料と技術DBを切り替える | 注意書きが混ざり、モデルが引数を取り違える余地が増える |

A の代償：技術DBの検索中は社内資料の検索が待たされる（同じ列に並ぶ）。少人数なら
1回数秒で済む。

### 4.2 サーバの構造

コーパスごとの違いを1つの値にまとめ、検索の本体は共通にする。

| | 社内資料（既存） | 技術ドキュメント（新規） |
| --- | --- | --- |
| ツール名 | `search_documents`（変更しない） | `search_tech_docs` |
| DB | `store.DB_PATH` | `store.DOCS_DB_PATH` |
| `rerank_floor` | 渡さない | `DOCS_RERANK_FLOOR` |
| 見出し | 「社内資料から N 件が見つかりました。」 | 「技術ドキュメントから N 件が見つかりました。」 |
| 0件・無関係のとき | 既存の `_FALLBACK`（一般知識は可、社内固有は推測しない） | 新しい文言（4.4） |
| DBが空のとき | 既存の文言 | 技術DBの取り込みコマンドを示す文言 |
| 埋め込みモデルの食い違い | 理由の文言をそのまま返す（既存） | 同じ |

- ストアとBM25索引は**コーパスごとに**持つ（`_State` を2つ）。片方の revision の
  変化でもう片方の索引を組み直さない
- リランカーの準備済みフラグは**プロセスで1つ**にする。モデルは同じなので2回
  確かめない
- 社内資料側の関数・文言・既存テストは変えない。共通化のために動かしてよいのは
  内部の構造だけで、`search_documents` の入出力は1文字も変えない

### 4.3 検索語は英語の疑問文で渡させる

翻訳は検索サーバでは行わない。Web 画面は生成モデルで英訳しているが、MCP の呼び手
（gpt-oss-120b）は自分で英語を書ける。MCP サーバに生成モデルを呼ばせずに済む。

- ツールの説明文に「英語の疑問文で書く」と、良い例・悪い例を1つずつ書く
- **日本語（ひらがな・カタカナ・漢字）を含む検索語は検索せず、英語で呼び直す
  よう指示する文を返す。** 日本語のまま検索すると、ほぼ確実に床で全件落ちて
  「0件」に見え、モデルは「資料に無い」と誤って結論する。0件の文言（4.4）は
  「再検索しない」と言うので、ここで止めないと呼び直す機会が無くなる
  （設計者の判断）

### 4.4 0件・無関係のときの文言

社内資料の `_FALLBACK` とは別の文を持つ。要点は次の3つである。

- context7・ウェブ検索・他のツールで補おうとしない（オフライン・社外に出さない
  という目的そのもの）
- 一般的な知識で答えてよいが、「技術ドキュメントDBでは確認できなかった」と断る
- 版（バージョン）に依存する記述は、推測であることを明示する

### 4.5 収録ライブラリをモデルに知らせる

ツールの説明文に、収録しているライブラリ名と版を並べる。起動時に
`docs_sources.toml`（唯一の設定）を読んで組み立てる。DBを開いて調べないのは、
開く操作が書き込みを伴うため（`_get_store` の docstring）。toml と DB の中身が
ずれる（取り込み忘れ）可能性は残るが、その場合は 0件の文言で正しく扱われる。

モデルは収録外のライブラリについて呼ばずに済み、呼んでも 0件で打ち切れる。

### 4.6 オフライン（GB10）

- リランカーの `hf_hub_download` は `HF_HUB_OFFLINE=1` でキャッシュだけを見る。
  `/etc/rag/rag.env`（`rag-web.service` と `rag-mcp.service` が読む）に入れる。
  Web 画面のリランカーも同じモデルなので、同じ1行で両方が止まる
- **事前に一度、外に出られる状態で `rag` ユーザーとしてモデルを取得しておく**手順を
  書く（`check_reranker()` を1回実行する）。キャッシュは `rag` のホーム
  （`/opt/rag/.cache/huggingface`）に入る。サービスも同じ `rag` ユーザーで動くので
  置き場所は食い違わない。vLLM のモデル（`/srv/models/huggingface`、コンテナが読む）とは
  別の置き場所である
- 埋め込み（`bge-m3`）は GB10 の vLLM（`127.0.0.1:8002`）で完結する

### 4.7 クライアント（手順書）

[docs/claude-code-gb10.md](../../claude-code-gb10.md) を更新する。

- `permissions.allow` に `mcp__local_docs__search_documents` と
  `mcp__local_docs__search_tech_docs` を足す
- context7 を外す：`claude mcp remove context7 --scope user`。保険として
  `permissions.deny` に context7 を入れ、誰かが登録し直しても呼ばれないようにする
- `~/.claude/CLAUDE.md` の「外部ドキュメントの参照」節を、技術DBを使う版に差し替える
  文面を載せる
- 動作確認に「技術DBの質問で `search_tech_docs` が呼ばれる」「context7 が呼ばれない」
  「収録外のライブラリで 0件 → 断って一般知識で答える」を足す
- 動作確認に「収録ライブラリを使うコードを書かせると、ツール名を言わなくても
  `search_tech_docs` が呼ばれる」を足す。質問されて調べるのと、コーディングの途中で
  自分から調べるのは別の振る舞いで、このツールが要るのは後者である。ローカルLLMは
  知っているつもりの API を調べずに書くことがあるので、ここで確かめる
  （`search_documents` の確認と同じく、同じ依頼を3回投げる）
- このツールは**コーディングのたびに毎回呼ばれるものではない**。呼ぶかどうかは
  モデルが決め、収録外のライブラリや調べる必要の無い編集では呼ばれない。検索は
  `search_documents` と同じ列に並ぶ（4.1 の代償）ので、毎回呼ばせる指示
  （hooks での強制など）は入れない

## 5. テスト（`tests/test_rag_mcp_server.py` に追加）

- `search_tech_docs` は `DOCS_DB_PATH` を開き、`search_documents` は `DB_PATH` を開く
- `search_tech_docs` は `rerank_floor=DOCS_RERANK_FLOOR` を渡し、社内資料側は渡さない
- 技術DBの結果・0件の文言に社内資料向けの語（「社内固有」）が入らず、社内資料の
  結果に技術DB向けの語が入らない
- 0件の文言が context7・ウェブ検索で補わないことを含む
- 日本語を含む検索語では検索を呼ばず、英語で呼び直す指示を返す
- 技術DBが空のときの文言が技術DBの取り込みコマンドを示す
- 技術DBの埋め込みモデルが設定と食い違えば、理由の文言を返し、DBを抱えたままにしない
- 片方のコーパスの revision が変わっても、もう片方の索引を組み直さない
- ツールの説明文に `docs_sources.toml` のライブラリ名が入る
- 既存の社内資料のテストは変更せずにすべて通る

外部通信が出ないことは単体テストでは測れないので、手順書の受け入れ確認で
`HF_HUB_OFFLINE=1` のまま初回検索が通ることを見る。

## 6. 確認済みの前提（設計時に手元のコードで確かめた）

- `MCPServer.tool()` は `description=` を受け取る（mcp 2.2.0）。説明文を起動時に
  組み立てて渡せる
- `docs_sources.toml` は `scripts.fetch_docs.load_sources()` で読める。各要素は
  `name` と `version` を持つ。`version = "0.0.0"` は版の記載が無い資料
  （ollama・csharp・go・mermaid・markdown）なので、説明文では版を出さない
- 技術DBが空のときの案内は `rag_web/app.py` と `scripts/check_retrieval.py` の
  `DOCS_INGEST_COMMAND` に二重にある。`rag_web.app` は FastAPI の画面一式を読み込むので、
  MCP サーバから import しない。さらにオフラインの GB10 では `fetch_docs` を走らせられない
  （`docs_source/` は git で追跡済みなので不要でもある）。MCP の案内は `ingest_source` の
  コマンドだけを示す。取り込みコマンドの文字列は `ingest/store.py` へ移して全員から使う
  （設計者の判断。二重管理を避けるため）
- `rag` ユーザーのホームは `/opt/rag`（`docs/server-deployment.md` 手順2）。
  `rag-mcp.service` は `ProtectHome=true` だが、ホームが `/home` の外にあるので影響しない。
  `ReadWritePaths=/opt/rag` なので、キャッシュの置き場所は書き込める
